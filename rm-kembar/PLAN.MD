# RM Kembar — Project Plan

## 1. Project Overview

**RM Kembar** is a web-based restaurant information system designed to digitize the full operational flow of a dine-in restaurant — from ordering and table reservation to payment, kitchen coordination, and sales reporting.

- **Target Users:** Customers, Admin (Kasir), Owner
- **Primary Device:** Mobile (smartphone via QR), secondary Desktop (Admin)
- **Core Stack (Proposed):** Laravel (Backend) · MySQL (Database) · Blade/React (Frontend) · Midtrans (Payment) · EvolutionAPI (WhatsApp Notifications)

## 3. Database Schema

### Design Principles
- **No enums anywhere** — all status/type fields use `varchar(30–50)`, validated at the application layer. Adding a new status or type never requires a migration.
- **Polymorphic relationships** on payments, ratings, and notifications so new models can attach to them without schema changes.
- **`meta` JSON column on every major table** — a safety valve for future fields that don't warrant their own column yet.
- **Soft deletes** on all user-facing tables — nothing is permanently lost.
- **Append-only logs** for stock and notifications — never updated, only inserted.
- **`settings` table** for all configurable values (tax rate, auto-cancel timeout, low stock threshold) so the owner can change them from the dashboard without a code deploy.
- **`conversations` table** as a parent for messages, so chat can scale to multiple agents or threads later.
- **`reservations.order_id`** FK links a reservation to the order it converts into — enables conversion rate reporting.
- All price/money columns use `decimal(12,2)` — the extra headroom costs nothing and prevents overflow on large catering orders.

> **Convention:** All tables use `id` (unsignedBigInteger, auto-increment), `created_at` and `updated_at` timestamps. Soft-deletable tables also have `deleted_at`.

### 3.17 Relationship Summary

```
users ──< orders ──< order_items >── menus >── menu_categories
users ──< caterings ──< catering_items >── menus
users ──< reservations ──> orders (when converted)
reservations >── dine_in_tables (assigned at arrival)
orders >── dine_in_tables
orders / caterings ──< payments          (polymorphic)
orders / caterings ──< ratings           (polymorphic)
menus ──< stock_logs                     (polymorphic reference)
users ──< conversations ──< messages
users ──< notifications                  (polymorphic notifiable)
dine_in_tables ── locked_by_order_id → orders
settings                                 (standalone config store)
```

### 3.18 Adaptability Rules (for future developers)

1. **Adding a new order status** (e.g., `refund_requested`) → add the string to your `OrderStatus` constants class. No migration needed.
2. **Adding a new payment method** → just pass the new string. No migration needed.
3. **Adding a new config value** → insert a row into `settings`. No migration needed.
4. **Adding a minor field to any model** → use the `meta` JSON column first. Only promote it to a real column once you're sure it's permanent and needs indexing.
5. **Adding a new notification type** → add a new type string to `NotificationType` constants. No migration needed.
6. **Adding a new order channel** (e.g., takeaway) → set `order_type = 'takeaway'` on `orders`. No migration needed.
7. **Adding multi-agent chat** → `conversations.assigned_to` already supports it. Just build the UI.
8. **Historical accuracy** → `order_items.menu_name`, `order_items.price`, `caterings.tax_rate`, and `caterings.dp_percentage` are all snapshotted at creation time. Changing menu prices or settings will never corrupt past records.

## 5. Order Status Flow

```
[Customer Submits Order]
        ↓
   PENDING (awaiting payment)
        ↓
   PAID & WAITING ARRIVAL
        ↓ (Admin scans/inputs code)
   ON-SITE (customer arrived)
        ↓ (Kitchen notified)
   PREPARING
        ↓
   COMPLETED
        ↓ (Table auto-released)
   TABLE → KOSONG
```

For **Catering**:
```
PENDING → DP PAID → CONFIRMED → DELIVERED → COMPLETED
```

For **Reservasi**:
```
BOOKED → CONFIRMED → ARRIVED / AUTO-CANCELLED (30 min timeout)
```

## 9. Architecture Decisions (Locked)

| # | Decision | Choice | Implications |
|---|---|---|---|
| 1 | **Frontend framework** | Inertia.js + React | Laravel handles routing and controllers normally. No separate API, no CORS, no Sanctum SPA cookie issues. Breeze scaffolds auth. React Router not needed — Inertia handles page navigation. |
| 2 | **QR Dine-In flow** | Static per-table URL | Each table gets a permanent QR → `yourdomain.com/order?table=7`. Customer scans, lands on menu page with table pre-selected. No dynamic QR generation needed per order. `dine_in_tables.qr_code_path` stores the pre-generated QR image. |
| 3 | **Reservasi table locking** | Guarantee availability only | Reservation does NOT lock a specific table. It reserves a slot (date + time + guest count). Admin assigns the actual table at arrival. Simplifies the locking logic significantly. |
| 4 | **Live Chat** | WhatsApp via EvolutionAPI | No separate in-app chat UI needed. Customer messages go to/from the restaurant's WhatsApp number via EvolutionAPI. `messages` table still logs conversation history. |
| 5 | **Kitchen Display** | Separate `kitchen` role | Kitchen staff get their own login with read-only access to active orders. No order management — just a live view of `preparing` status orders. Managed via Spatie Permission. |
| 6 | **Catering delivery fee** | Calculated | Add `delivery_fee` column to `caterings` table. Fee calculated based on distance or zone (logic TBD — flat rate per km or predefined zones). `total_price` = subtotal + tax + delivery_fee. |
| 7 | **Multi-branch** | Single branch only | No `branch_id` or multi-tenancy needed anywhere. Keeps schema and auth simple. |
